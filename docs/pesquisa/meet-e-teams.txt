

===== Google Meet (meet.google.com, 2025-2026 web app): RTCPeerCon

## Q: 1. Does Meet create RTCPeerConnection in the top frame? How is remote audio delivered (fixed small pool vs one per participant)? Is it attached to <audio> eleme 
[ confirmed ] Yes, top frame. Remote audio is a FIXED pool of 3 virtual audio streams (the 3 loudest speakers, re-assigned dynamically), not one receiver per participant; the real speaker is identified by the RTP CSRC. Normally each stream is attached by Meet to an <audio> element (srcObject = MediaStream) in the top document, but since about April 2026 Google has been A/B testing a variant with NO <audio> elements, so do not depend on them. Important nuance found live: Meet creates a throwaway RTCPeerConnection on page load of ANY /xxx-xxxx-xxx URL (even an invalid-code page), so PC creation is not an in-call signal. Hypothesis A (wrap RTCPeerConnection, read pc.getReceivers() audio tracks, mix to MediaStreamAudioDestinationNode, MediaRecorder) matches what attendee does in production: it collects every remote audio track from 'track' events and mixes them with WebAudio into a MediaStreamDestination that 'does NOT include the bot's audio'.

## Q: 1b. Is the remote-only requirement (exclude own microphone) satisfied, and which capture source is safer: receivers or <audio> elements? 
[ confirmed ] Receivers are the safer source. pc.getReceivers() only contains remote tracks, and Meet's SFU sends a mix-minus (your own voice is never in the 3 streams). Scanning page <audio>/<video> elements is riskier: vexa observed that in the lobby there are active media elements carrying self-preview audio tracks, so a DOM scan can pick up the local mic. If a DOM fallback is used, keep only elements whose audio track id belongs to some receiver.track.

## Q: 2. How to robustly detect in-call vs green room / waiting room ('Asking to be let in') / exit screen? 
[ confirmed ] No single signal is enough. (a) URL: meet.google.com path ^/[a-z]{3}-[a-z]{4}-[a-z]{3}(/|$) (query like ?authuser= / ?pli= can follow); exclude /, /landing, /new, /lookup/*, /unsupported. The URL is identical in green room, waiting room, in call, exit hall and the 'can't join' page, so it only gates the hook. (b) Leave button button[jsname="CQylAd"] (aria-label 'Leave call' / pt-BR 'Sair da chamada', icon <i class="google-symbols">call_end</i>) is present in call BUT ALSO while 'Asking to be let in'. (c) Admission-only signals: the captions button icon (google-symbols text closed_caption_off, or closed_caption if already on) and the chat icon appear only after admission (TranscripTonic); real participant tiles [data-participant-id] whose label is a person name (exclude the self 'Backgrounds and effects' tile, whose label starts with the visual_effects ligature, which exists in the lobby too). (d) Negative guards: no prejoin CTA (Join now / Ask to join; pt-BR 'Participar agora' / 'Pedir para participar'), no waiting text, no exit heading h1[jsname="r4nke"].roSPhc. (e) Best locale-free media signal: a hooked PC (not closed) with connectionState 'connected' and >=1 audio receiver whose track.readyState is 'live'. Recommended rule: inCall = urlMatches && leaveButtonPresent && captionsOrChatIconPresent && !exitHeading && (connectedPcWithAudioReceiver), debounced ~1.5-2 s. document.title is NOT a reliable in-call signal.

## Q: 2b. What is document.title during the call (en and pt-BR)? 
[ uncertain ] Not verified in a live call. Observed live: on the pre-join / 'can't join' page document.title is exactly 'Meet' in both en-US and pt-BR. Open-source code written in 2026 assumes in-call titles of the form 'Meet - <code>' or 'Meet - <title>' (with dash/en-dash/colon variants) and sometimes '<title> - Google Meet'. Treat document.title only as a last-resort title fallback after stripping a leading 'Meet' + separator or trailing 'Google Meet' + separator, and discard it if the remainder equals the meeting code or 'Meet'.

## Q: 3. How to get the meeting title (calendar event name) and meeting code? Is [data-meeting-title] still valid? Localized variants? 
[ confirmed ] [data-meeting-title] is STALE: per the WakaTime maintainer (2026-06-16) it 'is no longer present in an active Google Meet web meeting'. Many projects (AWS LMA, StreamDeck-Meet, whisper-daemon) still rely on it and will silently get nothing. Current best-effort order: (1) bottom-left meeting name element [jsname="NeC6gb"] or .u6vdEc (text = calendar event name, or the meeting code when there is no event; Meet fills it after a delay, TranscripTonic re-reads after 7 s; if its text equals the URL code, there is no title); (2) document.title with prefix/suffix stripping (uncertain format); (3) code fallback. Meeting code: from location.pathname regex ^/([a-z]{3}-[a-z]{4}-[a-z]{3}); fallback [role="heading"][aria-level="1"] whose text matches the code pattern (WakaTime). Title and code are user data, not localized; only UI chrome is localized, so pt-BR does not change these selectors.

## Q: 4. Participants list (best-effort) and how to exclude self 
[ confirmed ] Three tiers. (A) DOM tiles, no clicks: [data-participant-id] tiles; name from span.notranslate inside the tile (fallback data-self-name); self = tile containing [data-self-name] (or marker.closest('[data-participant-id]')); drop junk labels ('Google Participant (', 'spaces/', 'devices/') and the effects tile. Only rendered tiles are visible (large meetings / spotlight layout hide people), so accumulate names over the whole call into a Set. (B) People panel: div[role="listitem"][aria-label] (name in aria-label) but the panel must be open; do not auto-open it in a user's real call. (C) Protocol level, most complete but reverse engineered: attendee decodes the 'collections' RTCDataChannel (remote-created, deflate via pako + protobuf) and intercepts window.fetch responses of https://meet.google.com/$rpc/google.rtc.meetings.v1.MeetingSpaceService/SyncMeetingSpaceCollections (base64 protobuf). UserInfoList fields: deviceId(1), fullName(2), status(4: 1 in meeting, 6 not in meeting, 7 removed), isCurrentUserString(7, presence = self), displayName(29), parentDeviceId(21, screenshare device), isHost(34). This gives join/leave and an authoritative self flag. Speaking-glow classes (Oaajhc, HX2H7, wEsLMd, OgVli) and count badges are obfuscated and rotate.

## Q: 5. End-of-call signals: leave click, 'You left the meeting' screen, pc.connectionState, track 'ended' 
[ confirmed ] Use several, first one wins, then finalize once. (1) Exit hall in the same SPA document: heading h1[jsname="r4nke"] with class roSPhc appears (texts in en: 'You left the meeting', 'You've been removed from the meeting', 'The call ended because everyone left', 'Your host ended the meeting for everyone'); then a ~60 s countdown ('Returning to home screen' / pt-BR 'Voltando à tela inicial') navigates away. Prefer the structural heading over text. (2) Leave button click is only a hint: for hosts it opens a dialog (leave vs end for everyone), so do not finalize on click alone. (3) RTCPeerConnection: per the W3C spec, close() sets signalingState/iceConnectionState/connectionState to 'closed' and 'This does not fire any event', and stops transceivers 'with disappear', which ends receiver tracks WITHOUT firing 'ended'. So when Meet itself calls pc.close() on leave, neither connectionstatechange nor track 'ended' fires. Wrap RTCPeerConnection.prototype.close (or the instance) and also poll pc.connectionState and track.readyState every 1-2 s. connectionstatechange to 'disconnected'/'failed' fires on network loss but can be transient (reconnects). (4) Tab-level: chrome.tabs.onRemoved, URL leaving the code path (tabs.onUpdated / content-script pagehide). The MAIN-world MediaRecorder dies with the document, so the SW must finalize from already-persisted timeslice chunks on tab close. Also note the leave flow keeps the same URL, so a URL check alone never detects leaving.

## Q: 5b. pt-BR end/lobby strings ('Você saiu da reunião' etc.) 
[ uncertain ] Localized strings are fragile and partly wrong in open-source code. Verified live 2026-10-06 (pt-BR): 'Não é possível participar desta videochamada', 'Voltar à tela inicial', 'Voltando à tela inicial', 'Ativar câmera e microfone para a reunião?'. Verified from quoted real HTML: aria-label 'Sair da chamada'. Unverified but plausible: 'Você saiu da reunião', 'Você foi removido da reunião', 'Controles de chamada', 'Chat com todos'. Two projects disagree with the live text for 'Return to home screen' ('Voltar para a tela inicial', 'retornar à tela inicial'), proving that text matching is unreliable; English copy itself changed in Sep 2026 ('denied' to 'has denied').

## Q: 6. Pitfalls of hooking RTCPeerConnection on Meet: tamper checks, insertable streams / encoded transforms / E2EE 
[ confirmed ] No evidence that Meet detects or blocks the wrapper: attendee (production bots) replaces window.RTCPeerConnection with a plain function and Meet keeps working; vexa wraps it with prototype preserved; my live Proxy hook was used by Meet without errors. Concrete pitfalls: (a) Meet itself calls RTCRtpReceiver.createEncodedStreams() on a video receiver of its throwaway pre-join PC (feature detection, not E2EE, also reported by webrtcHacks in 2024). Never pass encodedInsertableStreams:true in the config and never call createEncodedStreams/transform on Meet's receivers (it can only be taken once and you would steal or break Meet's pipeline). (b) Workspace client-side encryption (CSE) encrypts in the sender's browser and decrypts in the receiver's browser, so receiver.track should still carry decoded plaintext audio (inference, not tested). (c) Meet CSP enforces require-trusted-types-for 'script': MAIN-world code must not assign HTML strings to innerHTML, use eval/new Function or set script src from strings; there is no connect-src/media-src restriction, so blob: and MediaRecorder are fine. (d) Proxy toString returns 'function () { [native code] }' instead of 'function RTCPeerConnection() { [native code] }', a tiny fingerprint; use a Proxy anyway because it preserves instanceof and statics (generateCertificate). (e) Throwaway/closed PCs and mid-call PCs (reconnect, ICE restart, breakout rooms, 'Switch here'): keep a registry, skip closed PCs, poll getReceivers() and hot-add new live audio tracks to the running mix. (f) A/B variant without <audio> elements and the long-standing Chromium behavior where a remote WebRTC track fed only to WebAudio can be silent unless it is also attached to a playing media element (crbug 933677 family, status in Chrome 154 unverified): if no Meet <audio> element holds the track, attach your own MUTED <audio> sink; vexa's unmuted mirror doubled the audio. (g) Create the AudioContext only after detection (the Join click gives user activation), call resume(), and never connect the mix to ctx.destination (double playback). (h) Background tabs: Chrome's intensive timer throttling does not apply while 'there's an RTCPeerConnection with an open RTCDataChannel or a live MediaStreamTrack', so 1-2 s polling in 3 simultaneous Meet tabs keeps working.

## Q: Prior art: does an existing open-source MV3 extension already do hypothesis A for Meet? 
[ confirmed ] Yes, closest prior art is the Vexa extension (clients/extension, Oct 2026): MAIN-world inpage.js + isolated content.js + service worker + offscreen, auto-start when the URL has a Meet code, and a 'recording tap' that combines all Meet <audio> elements into one MediaStream via AudioContext.createMediaStreamDestination and records it with MediaRecorder (timeslice 15 s), sending base64 chunks content -> background. Differences vs our needs: it is single-session (one state.tabId), auto-starts on URL only (also fires in green room), captures the local mic too, reads <audio> elements (vulnerable to the no-<audio> A/B variant and to the lobby self-preview), and its recording tap snapshots elements once at start (no hot-add). Its manifest registers the document_start MAIN-world webrtc-hook only for Zoom/Teams, and that hook is a no-op today.

RISKS
- Google is A/B testing an 'alternate way of orchestrating audio' with no <audio> elements (attendee, since 2026-04-01). If that variant also changes how audio reaches the page (e.g. not via RTCRtpReceiver tracks), hypothesis A gets no audio; keep fallback B (tabCapture) and log a 'no audio receivers after N s in call' diagnostic.
- Meet creates an RTCPeerConnection on every meeting-code page load (even 'can't join' pages) and closes it within seconds; treating PC creation or the first 'track' as 'in call' will create empty recordings for green room, waiting room and invalid links.
- pc.close() by Meet fires no connectionstatechange and no track 'ended' (W3C spec). A recorder that waits for those events will never finalize; must wrap close() and poll state.
- data-meeting-title vanished from the in-call DOM around June 2026; obfuscated replacements (.u6vdEc, jsname NeC6gb, jsname CQylAd, jsname r4nke/.roSPhc) can rotate without notice. Title extraction must degrade to the meeting code, never block recording.
- Leave button and call_end icon are also present while 'Asking to be let in'; text-based lobby/end detection breaks across locales (pt-BR strings in OSS projects disagree with the live UI) and English copy changes (Sep 2026).
- Remote audio is only the 3 loudest speakers at any moment: in large meetings with crosstalk, quieter simultaneous speakers are absent from what the browser receives. Per-speaker attribution from the mix is not possible without CSRC/collections decoding.
- Possible silent WebAudio input if a remote track is not attached to a playing media element (historic Chromium behavior, status in Chrome 154 not verified); and doubled playback if the mix is ever connected to ctx.destination or mirrored to an unmuted <audio>.
- Trusted Types enforcement on meet.google.com: any MAIN-world innerHTML/eval-style code throws and can break the hook silently.
- Unknown routing of screen-share (tab) audio from a presenter: may arrive on an extra receiver; record every live audio receiver, not a fixed 3.
- Not verified live in a real call (needs a Google login and a real meeting): green-room PC behavior for a valid meeting, in-call document.title, number of <audio> elements, pt-BR exit texts, behavior under Workspace CSE. These must be checked manually with chrome://webrtc-internals before relying on them.
- Legal/consent: Meet shows recording consent banners for its own recording; a silent local recorder of other participants may require consent under LGPD/company policy; not a technical risk but relevant to auto-start without click.
RECS
- Install the hook as a MAIN-world content script at document_start on https://meet.google.com/* (all_frames false is enough; Meet's PC is in the top frame). Use new Proxy(RTCPeerConnection, {construct}) so instanceof, prototype and statics keep working; register every PC in a Set; wrap RTCPeerConnection.prototype.close to mark the PC closed and emit an event.
- Do NOT start on PC creation or URL. Start recording only when: URL matches ^/[a-z]{3}-[a-z]{4}-[a-z]{3} AND some registered, not-closed PC has connectionState 'connected' AND has >=1 receiver with track.kind 'audio' and readyState 'live' AND button[jsname="CQylAd"] (or google-symbols 'call_end') is present AND a captions/chat google-symbols icon is present AND no h1[jsname="r4nke"]/.roSPhc heading; require the condition stable for ~2 s.

Poll all PCs' getReceivers() every 1-2 s and hot-add new tracks (reconnects, breakout rooms, presenter audio). If a track has no playing Meet <audio> element, attach a muted hidden <audio> with that stream to keep it flowing.
- Record with MediaRecorder('audio/webm;codecs=opus') on destination.stream with a 5 s timeslice and persist every chunk immediately (MAIN -> ISOLATED -> SW -> IndexedDB keyed by tabId+sessionId), because the document and recorder die on tab close/navigation and the SW must be able to finalize from stored chunks.
- End detection (first wins, idempotent finalize): wrapped pc.close() or polled connectionState 'closed' on the PC that carried audio; all audio receiver tracks readyState 'ended'; exit heading h1[jsname="r4nke"]/.roSPhc appears; URL leaves the code path; chrome.tabs.onRemoved. Treat a leave-button click only as a hint (host dialog). Treat 'disconnected'/'failed' as end only after a grace period (~20-30 s) without recovery.
- Metadata: platform 'google_meet'; code from URL; title from [jsname="NeC6gb"] || .u6vdEc (re-read for ~10 s after join and again at end; discard if equal to the code), then document.title with prefix/suffix stripping, else the code; never depend on [data-meeting-title]. Start/end timestamps from the in-call/finalize transitions, not page load.

Optional later upgrade: decode the 'collections' data channel / SyncMeetingSpaceCollections RPC like attendee for authoritative names and join/leave times.
- Avoid any innerHTML/eval/new Function in MAIN-world code (Meet enforces Trusted Types). Do not pass encodedInsertableStreams or call createEncodedStreams on Meet's receivers.
- Before shipping, verify manually in a real meeting with chrome://webrtc-internals open: number of audio receivers (expect 3), whether the main PC exists in the green room and in 'Asking to be let in', whether Meet calls pc.close() on leave, in-call document.title in en and pt-BR, and that the recording contains only remote voices (speak yourself and confirm silence in the file). Repeat with 3 tabs/meetings at once to confirm per-tab isolation and that background tabs keep recording.
- Keep fallback B (tabCapture via action click or keyboard command) for when the hook finds no audio receivers within ~15 s of in-call detection; note tabCapture captures the tab output, which for Meet is also remote-only (your mic is not played back locally).


===== Microsoft Teams web (teams.microsoft.com v2, teams.cloud.mic

## Q: Q1a. Where does Teams web create RTCPeerConnection: top frame, iframe or worker? 
[ confirmed ] In a window, never a worker. In the anonymous light-meetings app the calling stack runs in the top-level tab document. For the signed-in v2 client this is inferred, not proven: production bots patch window.RTCPeerConnection and read Teams' calling globals from the same realm, and that works. Teams does use workers and worklets, but for other jobs: encoded-stream transforms and the WASM audio codec, wasmcv (video), a timer worker, CDL and telemetry, plus AudioWorklets for VQE, decoder, renderer and timer. Teams also creates several short-lived probe PCs: an ICE local-ip probe (data channel 'local-ip-hydra-player-ice-candidates'), a relay probe (tryCreatePc) and a rollback-support check, alongside the real media PC. One caveat for the signed-in client: its pre-join UI can render inside the first same-origin iframe. So inject with all_frames:true and match_origin_as_fallback:true, and make the hook idempotent per realm.

## Q: Q1b. Does Teams in the browser use SlimCore, or the browser's WebRTC? 
[ confirmed ] In the browser it uses the browser's own WebRTC (unified-plan RTCPeerConnection). SlimCore appears in the web bundle only on Electron/desktop and VDI branches.

## Q: Q1c. How is remote audio delivered? Is it a single mixed track from the media server? 
[ confirmed ] Yes on the normal path: one server-side mix arrives on one audio receiver, and its MediaStream id is prefixed 'mainAudio'. Vexa also saw a redundant track (for example 'dominantSpeaker-N') whose audio is already in the mix, so mixing every remote track doubles the words. Who is talking comes from RTP CSRCs (receiver.getContributingSources()), which Teams maps to participants with participant.hasAudioSource(csrc). Teams plays the chosen stream through one <audio> element it creates and appends to document.body (autoplay, setSinkId for the output device). When a speaker-gain config is set, it routes through its own AudioContext gain node into a MediaStreamDestination first. The audio is decoded PCM, so a MediaRecorder or WebAudio tap in the page can read it.

## Q: Q1d/Q5. Can Teams' insertable-streams path hide the decoded audio from RTCRtpReceiver tracks? 
[ confirmed ] Yes, potentially, when a server-side config flag is on. Teams web ships an 'AudioWasmCodec' path behind config.useInsertableStreams.audioWasmCodec.enable, also used for spatialAudioEnabled. On that path it negotiates proprietary codecs (MUCHv2 'x-much2' PT113, MUCHv3 'x-much3' PT96, SatinFB PT109) that appear in the SDP as 'L16'. Encoded frames are pulled with createEncodedStreams or RTCRtpScriptTransform into an 'encoded-stream' worker, decoded in WASM, written into MediaStreamTrackGenerator tracks ('unmixedAudioProvider'), and mixed in Teams' own 48 kHz AudioContext into a MediaStreamDestination. On 'usedDecoderChanged' Teams switches its <audio> element from webrtcAudioRecvStream to that destination stream, and CSRCs then come from decoder events, not receiver.getContributingSources(). In that mode the mainAudio receiver track is not the audible signal and may be silent. Whether the flag is on for a given tenant or user is unknown.

## Q: Q3. Meeting title and participants (roster) selectors; how to exclude self. 
[ confirmed ] Best source, in the MAIN world: the Teams call object. Light meetings exposes it as window.callingDebug.observableCall; v2 as window.msteamscalling.deref().callingService.getActiveCall(). It gives .threadId, ._callId, .state, .callerMri (self MRI with the 8: prefix), .participants (remote, each with id, displayName, state, isServerMuted, endpoints, meetingRole and hasAudioSource(csrc)) and .localSignalingParticipant (self: id, displayName). Self is excluded by construction: .participants holds only remote people, and attendee adds the local participant separately. Drop participants with state 7 (in the lobby) and those without a displayName. DOM fallback for the roster, which only renders while the People pane is open: rows have data-cid='roster-participant' and data-tid='<section>-<displayName>', where section is participantsInCall, attendeesInMeeting, participantsInLobby (skip), participantsFromMeeting, participantsFromThread or participantsFromTeamSuggestions. The aria-label also carries the name. Speaking tiles: [data-tid='voice-level-stream-outline'] inside [data-stream-type][data-tid] wrappers, whose data-tid is the display name. Title: document.title before ' | Microsoft Teams' (light meetings), or [data-tid='meeting-header-title'] (its title attribute holds the meeting subject; seen in the pre-join and lobby header). Avoid Fluent hashed classes such as ___2u340f0, which rot between builds.

## Q: Q4. End-of-call signals and the post-call screen. 
[ confirmed ] In order of reliability: (1) the call object's state leaves 3 and reaches 6 then 7 (Disconnecting, Disconnected). LocalHold (4) is not an end. (2) Teams' streamRemoved() runs for the audio modality: it stops the renderer and sets the <audio> srcObject to null; the mainAudio track fires 'ended'; the PC connectionState becomes 'closed'. (3) The trouter WebSocket text frame '3:::{...url ending in conversation/conversationEnd/...}' arrives (attendee uses it, with a subCode for 'denied'). (4) The DOM loses #hangup-button and #raisehands-button (Meeting-BaaS uses the missing raisehands button as its removal signal). Anonymous post-call screen: [data-testid='calling-anon-meeting-end-screen'], [data-testid='calling-anon-meeting-end-screen-give-feedback-button'] and [data-testid='anon-meeting-end-screen-rejoin-button']. Signed-in v2 usually goes back to the app or shows a call-quality survey; there is no stable id for that. Teams' internal screen enum is CallScreen=0, PrejoinScreen=1, LeaveMeetingScreen=2, CallingEndScreen=3, EmptyScreen=4. Removal texts (localized): 'You've been removed from this meeting', 'Meeting ended', 'Call ended'. Also handle the tab closing (pagehide) and navigation away.

## Q: Q5a. Does Teams web use E2EE that would hide decoded audio? 
[ confirmed ] No. Microsoft lists Web (and VDI and CVI) as unsupported for E2EE meetings and one-to-one calls, and browser participants are blocked from E2EE meetings. So any meeting a browser tab is actually in carries normal (service-decryptable) media, and the browser decodes it to PCM. The insertable-streams caveat from Q1d is about a proprietary codec, not encryption.

## Q: Q5b. Tamper detection or automation detection? 
[ confirmed ] No RTCPeerConnection tamper checks were found. The only 'native code' checks are Babel's wrapNativeSuper helper, and attendee's crude override works in production: a plain function with no prototype link and no static generateCertificate, with addTrack and addTransceiver re-attached. Teams does score automation and bots on anonymous join: navigator.webdriver, the webdriver attribute, 'playwright', 'selenium' and 'Cypress' in window, phantom globals, a minimal viewport, missing user activation, a UTC timezone, and name words such as Assistant, Recorder, Bot, AI and Agent. That matters for Playwright tests, not for the user's real Chrome profile.

## Q: Q5c. Do page CSP and Trusted Types constrain a MAIN-world recorder on Teams? 
[ confirmed ] Yes. The page CSP applies to MAIN-world content scripts. Teams v2, teams.live.com and light-meetings all send require-trusted-types-for 'script' with a fixed allowlist of trusted-types policy names, a nonce-based script-src without blob:, and worker-src 'self' blob:. Consequences: never assign to innerHTML or script.src, and you cannot create your own Trusted Types policy (the names are allowlisted). An AudioWorklet loaded from a blob: URL would be blocked, because worklets fall under script-src. MediaRecorder, WebAudio graphs, MediaStream APIs and window.postMessage are unaffected. If you need a worklet, load it from a web_accessible chrome-extension:// URL, as vexa ships vexa-pcm-worklet.js; verify that it loads.

## Q: Recent change: domain migration to teams.cloud.microsoft 
[ confirmed ] Teams for organizations is moving its web client from teams.microsoft.com to teams.cloud.microsoft. The automatic redirect was due by 2026-09-30; admins can postpone with UseUnifiedDomain until 2026-12-31, and from 2027-01-01 there is no opt-out. teams.live.com (consumer) is unaffected. Manifest matches, URL parsers and host checks must include https://teams.cloud.microsoft/*. Attendee's domain allowlist still lacks it; vexa and Meeting-BaaS already include it.

## Q: Is the user's own voice excluded from what a MAIN-world receiver tap records? 
[ uncertain ] The local microphone is a sender track and never shows up among the RTCRtpReceivers, so a receiver tap or <audio> tap never records the raw mic. Whether the server mix leaves out your own voice (a typical N-1 mix) is plausible but has not been documented or measured for Teams. In the WASM unmixed path, Teams builds the mix from remote streams in its own AudioContext.

## Q: Can one signed-in Teams account be active in three meetings at once (one per tab)? 
[ uncertain ] Probably not as active calls. With the same account, joining a second meeting puts the first on hold (CallState LocalHold=4), and on-hold calls receive no media, so the recording goes silent. Separate accounts (different tenants or Chrome profiles) or anonymous light-meeting joins in separate tabs are independent. This matters for the user's three simultaneous calls if they are all Teams with one account.

## Q: What did the closest real extension (vexa in-tab extension) choose for Teams, and why? 
[ confirmed ] Vexa's MV3 extension does not use a WebRTC hook for Teams. It ships webrtc-hook.js as a disabled no-op at document_start in the MAIN world with all_frames, and records Teams through offscreen tabCapture minted on the toolbar click, plus DOM speaker hints. Their reason: their hook mirrored each remote track into extra audible <audio> elements, which doubled the audio and created per-participant channels. The lesson for hypothesis A: tap the stream silently (MediaStreamAudioSourceNode into a MediaStreamDestination for MediaRecorder, never connected to the speakers) and pick only the stream Teams renders. Hypothesis B (tabCapture) needs an extension invocation and stays the robust fallback, because it records the final tab output whatever the codec path.

RISKS
- The proprietary WASM audio codec path (useInsertableStreams.audioWasmCodec, MUCH and SatinFB disguised as L16, spatial audio) is server-flighted. When it is on, the mainAudio RTCRtpReceiver track may be silent or garbage, while the audible audio comes from Teams' own AudioContext and MediaStreamTrackGenerator streams. A recorder that only taps receiver tracks would record silence with no error.
- The 'mainAudio' stream-id prefix is a vendor string, matched as such by attendee and vexa. If it is renamed, a strict filter captures nothing. Mixing all tracks instead double-feeds the redundant dominant-speaker track and repeats words.
- The toolbar (with #hangup-button) and a PeerConnection can exist while in the lobby or staging. Starting the recording on 'hangup visible' or 'track arrived' records lobby silence and sets a wrong start time.
- Several short-lived probe PCs (ICE local-ip, relay probe, rollback check) also go through the wrapper. Keep only connected PCs that carry a mainAudio receiver, and prune closed ones.
- Teams internals (window.callingDebug.observableCall, window.msteamscalling WeakRef, window.lime, participant.hasAudioSource, callerMri) are undocumented and can change in any weekly build. Light meetings and v2 expose different globals.
- The domain moves to teams.cloud.microsoft (redirect due 2026-09-30, opt-out ends 2026-12-31). Missing it in manifest matches means no injection at all for most work tenants.
- Trusted Types and CSP apply to MAIN-world code: innerHTML, blob: worklets and custom TT policies throw. Errors land in Teams' own telemetry and console.
- With one signed-in account, Teams places the other calls on hold (LocalHold=4) when joining another meeting, so parallel Teams recordings in three tabs with the same account may be silent. This is based on an older Microsoft Q&A answer and should be retested on v2.
- Teams scores automation signals (navigator.webdriver, 'playwright' in window, names containing Bot, Recorder, AI or Agent). Playwright Chromium test joins may be labeled as bots, held in the lobby or shown a captcha, so tests can fail for reasons that do not happen in the user's real Chrome.
- 1:1 Teams calls may be peer-to-peer rather than via the media server. The stream-id label and CSRC behaviour there were not verified.
- Using the fallback B tabCapture while Teams routes its <audio> through setSinkId to a non-default output device has not been verified for this setup. Test it before relying on it.
- AudioContext created at document_start, before any user activation, starts 'suspended'. It must be resumed after the user clicks Join (sticky activation), otherwise MediaRecorder gets silence.
- Text selectors ('Someone will let you in shortly', 'You've been removed from this meeting', 'Leave') are localized; the user's UI may be pt-BR. Fluent hashed classes rot between builds.
RECS
- Manifest: register the MAIN-world hook at run_at document_start, world MAIN, all_frames true, match_origin_as_fallback true. Matches: https://teams.microsoft.com/*, https://teams.cloud.microsoft/*, https://teams.live.com/*, and optionally https://*.teams.microsoft.us/*. Make the hook idempotent per realm.
- Capture priority for Teams, all silent taps that never connect to the speakers. (1) Wrap the HTMLMediaElement.prototype.srcObject setter, and as a backup poll document.querySelectorAll('audio'), to get the MediaStream Teams assigns to its single body-appended <audio>. This covers the normal path, the WASM decoder path and the speaker-gain path. (2) If that is unavailable, use the RTCRtpReceiver track whose streams[0].id starts with 'mainAudio' (case-insensitive). (3) After about 15 s with no mainAudio, or 20 s of a provably silent pick, fail open to all remote audio tracks and log it, as vexa does. Feed the chosen stream into an AudioContext MediaStreamDestination and record with MediaRecorder; do not attach a new audible element.
- Start recording only when the Teams call state equals 3 (Connected), read every second from window.callingDebug?.observableCall?.state or window.msteamscalling?.deref?.()?.callingService?.getActiveCall?.()?.state. DOM fallback: #hangup-button present AND no lobby or pre-join markers (prejoin-join-button, calling-lobby-screen, lobby text). Pause on 4 or 5 (hold) without closing the file. Finalize on 6 or 7, on hangup gone for more than 5 s with the mainAudio track ended, on PC 'closed', on the anon end screen [data-testid=calling-anon-meeting-end-screen], or on pagehide.
- Metadata per tab. Platform from the host. Thread id from activeCall.threadId, the URL, or the regex 19:meeting_[A-Za-z0-9_-]+@thread.v2 over the URL, DOM and storage (vexa approach). Short meeting code from /meet/<digits>. Title from document.title minus the ' | Microsoft Teams' suffix (light meetings) or [data-tid=meeting-header-title][title], captured at pre-join. Participants from activeCall.participants (displayName, id; skip state 7 and empty names), deduplicated over time, with self from localSignalingParticipant or callerMri. DOM roster fallback: [data-cid=roster-participant] with data-tid prefixes participantsInCall- and attendeesInMeeting-.
- Optional speaker timeline: poll receiver.getContributingSources() every 100 ms on the mainAudio receiver and map CSRCs with participant.hasAudioSource(csrc) (attendee). Under the WASM codec path CSRCs come from the decoder instead, so treat the timeline as best-effort.
- Key everything by tabId in the service worker, since each Teams tab is its own realm with its own call object. Warn the user that three Teams calls on the same account will put two on hold; use separate accounts or Chrome profiles if they need three live Teams calls.
- Test matrix before trusting it. Signed-in v2 on teams.cloud.microsoft, teams.live.com personal, and anonymous light-meetings. Meeting vs 1:1 call. For each, compare RMS of the mainAudio receiver against Teams' <audio>.srcObject, and confirm your own voice is absent (others muted). Run in real Chrome 154; in Playwright Chromium, expect Teams' automation scoring to flag the join.
- Keep fallback B (tabCapture via an action click or keyboard command, consumed in an offscreen document, audio routed back to the speakers) for when the MAIN-world tap yields silence. Surface a visible 'not recording' alert instead of saving a silent file.
- Keep MAIN-world code free of innerHTML and of blob:/data: worklets because of Teams' Trusted Types CSP. If PCM is needed, load the worklet from a web_accessible chrome-extension:// URL and verify it loads; MediaRecorder needs no worklet.
