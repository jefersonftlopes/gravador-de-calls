## Q: 3. @crxjs/vite-plugin 2.x and world: MAIN: does the loader break document_start? Workaround? 
[ confirmed ] The problem was real and is now solved, but only in recent versions. Before 2.3.0, MAIN-world scripts failed outright because the loader called chrome.runtime.getURL (undefined in MAIN world), issue #695. 2.3.0 (2025-12-08, PR #1080) added MAIN-world support through a dedicated loader that still does an async dynamic import() of the real chunk, so page scripts can run before the hooks are installed. 2.5.0 (2026-06, PR #1158, issue #1101) added real IIFE content scripts: name the file *.iife.ts or list it in crx({ contentScripts: { standaloneFiles: [...] } }); the build emits a self-contained synchronous bundle referenced directly by the manifest. In dev (serve) mode, manifest-declared IIFE scripts still went through the async -loader until PR #1226 / #1185 (merged 2026-09-12/13, issue #1225), released in 3.0.0 (2026-09-24). 3.0.0 also warns when a document_start script uses the async loader, and drops CommonJS (ESM only). Scripts with no imports/exports have skipped the loader since 2.0.0. Recommended workaround: crxjs >= 3.0.0 with *.iife.ts or standaloneFiles (correct timing in dev and build). If staying on 2.x, a separate esbuild or vite lib build with format 'iife' (watch mode) emitting a plain file is the safe path, as issue #1101 describes. The cwd project (zapdesk/extension) resolves '^2.0.0-beta.28' to 2.7.1 and its own precedent injects MAIN-world code by appending <script src=chrome.runtime.getURL(...)> from an ISOLATED script at document_idle (src/content/index.ts:15-16, public/vendor/*.js); that pattern is async and cannot meet the document_start requirement, so diverging from it must be declared.

## Q: 4. chrome.runtime messaging: still JSON? Max size? Structured clone? Best way to stream ~30KB chunks every 5s? 
[ confirmed ] By default, still JSON in Chrome (undefined becomes null, no ArrayBuffer/Blob/Map). Max message size is 64 MiB. NEW (flag as recent): since Chrome 148 (blog of 2026-04-22) an extension can opt in with the top-level manifest key "message_serialization": "structured_clone"; then runtime.sendMessage and runtime.connect Ports between extension contexts (content scripts included) carry Map, Set, Date, BigInt, Error, File and Blob; typed arrays/ArrayBuffer are copied, never transferred; SharedArrayBuffer fails; toJSON() is ignored; native messaging stays JSON; extension-to-extension messaging fails if formats differ; web pages using externally_connectable adapt automatically. Below 148 or without the key it silently stays JSON, so pair it with minimum_chrome_version 148. Best streaming design: MAIN -> ISOLATED via window.postMessage (already structured clone, Blob works), then ISOLATED -> extension via one long-lived Port. With JSON, send base64 strings (about 33% overhead; 30KB becomes about 40KB, trivial against 64 MiB); never Array.from(bytes). With structured_clone, post the Blob or Uint8Array directly. Add a sequence number and ack, keep unacked chunks in memory in the content script, and reconnect on onDisconnect, because MediaRecorder timeslice chunks are only decodable when concatenated in order from the first one. The Port can terminate in the offscreen document instead of the SW (runtime.connect reaches onConnect in all extension pages), letting the offscreen page write to the extension-origin IndexedDB directly.

## Q: 6. Offscreen documents: reasons, one per extension, several concurrent captures, blob URL to downloads.download from SW, size limits 
[ confirmed ] Reasons include BLOBS (URL.createObjectURL), USER_MEDIA (getUserMedia, which is how tabCapture stream IDs are consumed), AUDIO_PLAYBACK, DISPLAY_MEDIA, WEB_RTC, WORKERS, LOCAL_STORAGE and others; pass several in the reasons array. Only one offscreen document can be open per installed extension (two with split-mode incognito); a second createDocument fails with 'Only a single offscreen document may be created.', so guard creation with a mutex and check runtime.getContexts (or offscreen.hasDocument, which needs Chrome 150+). AUDIO_PLAYBACK alone closes the document after 30 s without audio, but Chromium only closes it when none of its reasons is still active, so combining it with USER_MEDIA/BLOBS keeps it open. Only the runtime API is available inside, so chrome.downloads must be called from the SW. Nothing limits concurrent getUserMedia tab streams or MediaRecorders in one document: hold N captures keyed by tabId; closing or recreating the document kills all of them. Blob URL hand-off works: downloads.download called from the SW has no frame, and DownloadManagerImpl then builds a blob URL loader factory from the extension's storage partition, where the offscreen document registered the URL. The blob URL dies when the creating document closes or revokes it, so revoke only after downloads.onChanged reports complete or interrupted. Size: no extension-specific limit; blobs spill to disk; an hour of 32 kbps Opus is about 14 MB. Use unlimitedStorage so IndexedDB never hits quota; chrome.storage.local is the wrong place for audio.

## Q: 7. chrome.downloads.download: subfolder filenames, allowed characters, lengths, saveAs:false vs 'Ask where to save', conflictAction, symlink 
[ refuted ] Filename is relative to the user's configured download directory (chrome://settings/downloads, not necessarily ~/Downloads); subdirectories are allowed and created automatically; absolute paths, empty paths and '..' are rejected. Chrome first replaces '%' with '_', then requires every path component to pass IsSafePortablePathComponent, otherwise the call fails with 'Invalid filename'. Rejected in any component on every OS: " * / : < > ? \ | , control chars (Cc), format chars (Cf, which includes zero-width joiners in emoji sequences), Unicode non-characters, leading or trailing whitespace, '.' or '~' (so no hidden '.folders' and no 'name.'), Windows reserved names even on macOS (CON, PRN, AUX, NUL, COM1-9, LPT1-9, CLOCK$, desktop.ini, thumbs.db, CONIN$, CONOUT$), and .lnk/.local/.scf/.url extensions. Watch out: '14:30' is invalid, use '14h30'; titles with '/' or ':' must be sanitized. Length: Chrome truncates only the final file name to the filesystem limit (APFS 255 bytes) minus the 11-byte '.crdownload' suffix; directory components are not truncated, so keep each well under 255 UTF-8 bytes. A matching file extension and Blob type (audio/webm, application/json) avoids extension rewriting. saveAs:false does NOT suppress the dialog when the user enabled 'Ask where to save each file': saveAs only forces a prompt when true; otherwise the PromptForDownload pref still prompts (exceptions: policy-managed download directory, auto-open file types). conflictAction: uniquify (default, adds ' (1)' before the extension of the FILE, never of the folder), overwrite (replaces, but another in-progress download to the same path still becomes a conflict), prompt (file chooser). Symlinks: Chrome 154 resolves the real path and, if a subfolder symlink leads outside the download directory, moves the target to the download root and treats it as not writable, which triggers a Save As dialog. So a symlink to a folder outside Downloads does NOT work silently (a symlink staying inside the tree, or Downloads itself being a symlink, is fine). Exact milestone of this check not verified, but it is in 154. UI: each download shows in the toolbar download bubble (auto-opens when done unless the user turns off 'Show downloads when they're done'). downloads.setUiOptions({enabled:false}) (Chrome 105+, needs 'downloads' + 'downloads.ui', warning 'Manage your downloads') hides the whole profile's download UI while any extension keeps it disabled, so toggle around your own downloads; downloads.erase({id}) removes the history entry without deleting the file. setShelfEnabled is deprecated since 117. Files land first as .crdownload, so a whisper watcher should wait for info.json written last.

## Q: 1. Is the Chromium bug where a remote WebRTC track fed into WebAudio (or MediaRecorder) is silent unless attached to an HTMLMediaElement sti 
[ confirmed ] Yes, still present in Chrome 154 and CfT 151. Bug: crbug 933677, now issues.chromium.org/40094084, title 'MediaStream from RTC is silent (in WebAudio, MediaRecorder, etc.) if not attached to a media element'. Status Assigned, P2/S4, open since 2019-02-20; last activity 2026-06-11 was only a CC change. Merged duplicates include crbug 952700 (MediaRecorder), 1115402, 1324172, 1479349, 1485078, 988432. Root cause (Chromium dev comment, 2022-12-16): playback is a pull model. WebRtcAudioRenderer pulls the WebRTC mixer, and each track pushes to WebAudio sinks only during those pulls. With no renderer, nothing is decoded. Workaround, measured: a muted Audio element with srcObject = new MediaStream([remoteTrack]) is enough. play() is not needed, the element does not need to be in the DOM, and volume=0 works as well as muted=true. Pausing the element afterwards does not break the tap. Bigger finding: ANY element in the same frame playing ANY remote WebRTC audio primes ALL remote tracks of ALL peer connections in that frame. One shared WebRtcAudioRenderer per frame pulls the whole mixer. So on Meet or Teams, where the page already plays remote audio through elements, the tap works without priming. Chrome has no createMediaStreamTrackSource (typeof 'undefined').

## Q: 2. AudioContext autoplay: with sticky activation from the Join click, is new AudioContext() running even when created later from a timer or  
[ confirmed ] After the Join click (sticky activation), new AudioContext() created from a timer seconds later starts 'running'. A context created BEFORE the click stays 'suspended' and does not auto-resume. Calling resume() from a timer afterwards succeeds without a new gesture. Blink's IsDocumentAllowedToPlay has no visibility check, so the background state should not matter. Hidden state was NOT tested empirically: headless cannot hide a tab. A document is also allowed to play with no gesture at all when any of these is true. (a) It is capturing mic or camera (DocumentIsCapturingUserMedia). (b) Its origin has persisted mic or camera permission ALLOW. This is new: kAutoplayBypassForMicCamera, absent in M146, disabled in M147, ENABLED_BY_DEFAULT since M148, verified on 154. (c) MEI is high (desktop default on). (d) Enterprise policy AutoplayAllowlist or AutoplayAllowed is set. (e) A same-origin renderer-initiated navigation followed sticky activation (HadStickyUserActivationBeforeNavigation): location.reload() from page script kept 'running' and hasBeenActive=true. A browser-initiated reload or navigation (Cmd+R, omnibox, session restore; page.reload() in Playwright) LOSES sticky activation and returns 'suspended' unless (a) through (d) apply. Strategies: create the context lazily when the first live remote audio track appears. If its state is 'suspended', call resume() in a capture-phase pointerdown/keydown listener in the MAIN world, retry when getUserMedia starts, and surface a badge. Alternatively avoid WebAudio entirely: MediaRecorder directly on the remote track needs no AudioContext, and its timeline stayed continuous in tests. In practice, a call page with live mic capture or saved mic permission will always be allowed.

## Q: 3. MediaRecorder: does Chrome record only the first of multiple audio tracks? Supported audio mimeTypes in Chrome 154? Are timeslice chunks  
[ confirmed ] Only the first audio track is recorded (Chromium logs 'Only recording first audio track.'). Adding a track to the recorded MediaStream during recording fires InvalidModificationError and the recorder goes 'inactive'. So mix with WebAudio into one MediaStreamAudioDestinationNode track; never record new MediaStream([...remoteTracks]). isTypeSupported on Chrome 154 (same on CfT 151): true for audio/webm, audio/webm;codecs=opus, audio/webm;codecs=pcm, audio/x-matroska;codecs=opus, audio/mp4, audio/mp4;codecs=opus, audio/mp4;codecs=mp4a.40.2. False for audio/ogg (any), audio/wav, audio/mpeg, audio/aac, audio/flac. Concatenating all timeslice chunks in order from chunk 0 gives a valid, decodable WebM. A truncated prefix (crash mid-call) also decodes up to the last complete block. A chunk alone without chunk 0 is not decodable (no EBML header). With a timeslice, the WebM has no Duration/Cues (ffprobe duration N/A). That is harmless for ffmpeg, which decodes the full length, and for whisper (it needs conversion anyway). It only matters for seeking in players. Change since 2025: Chromium issue 40482588 'MediaRecorder: consider producing seekable WebM files' was fixed in M138, temporarily disabled, then re-enabled in M140+. Since then, start() WITHOUT a timeslice yields a seekable WebM with duration. With a timeslice it is still live/non-seekable, which is what we need for durability. Cheap fixes: ffmpeg -i in.webm -c copy out.webm (remux adds duration), or the conversion to WAV for whisper. If a middle chunk is lost in transit, the decode still succeeds but the timeline collapses (10 s recording gives an 8.94 s WAV). ffmpeg -af aresample=async=1 fills the gap with silence (9.96 s), which keeps transcript timestamps aligned.

## Q: 4. Background tabs: are pages with an active RTCPeerConnection / live track / audio exempt from intensive throttling? Will setInterval(1000) 
[ confirmed ] Intensive wake-up throttling (1 wake-up per minute) does not apply when 'an RTCPeerConnection with an open RTCDataChannel or a live MediaStreamTrack' exists, or when the page was audible in the last 30 s. The hidden page still gets normal throttling: timers are aligned to 1 s. So setInterval(1000) keeps firing about once per second, with jitter of up to ~1 s. MediaRecorder dataavailable is not timer-driven: WriteData emits a slice when muxer output arrives after the timeslice elapsed, so it keeps firing. The WebAudio graph keeps running even with nothing connected to ac.destination. After 30 s of silence, SilentSinkSuspender swaps in a fake sink that keeps calling Render() at real-time pace (45 s test: decoded 44.93 s, no silence gaps). Freezing (Energy Saver since M133, plus 'infinite tabs freezing', which is still FEATURE_DISABLED_BY_DEFAULT) excludes pages with CannotFreezeReason kWebRTC, kCapturingAudio/Video and kAudible/RecentlyAudible, for all freezing types. RISK: tab discarding (Memory Saver/proactive discard) has NO WebRTC exemption. It protects only visible, audible or recently audible, capturing audio/video, mirrored, PiP, pinned and other states, plus kExtensionProtected. A call where the user's mic is off and nobody speaks could become discard-eligible. Mitigation: chrome.tabs.update(tabId, {autoDiscardable:false}) while recording. After the call ends and the PC closes, the exemptions disappear (intensive throttling after 5 min hidden), so finalization must be event-driven, not timer-driven.

## Q: 5. If the user mutes the tab in Chrome, does remote WebRTC audio still reach WebAudio/MediaRecorder? 
[ confirmed ] Yes. Tab mute (extension chrome.tabs.update muted, the tab audio indicator, or 'Mute site', which all go through SetTabAudioMuted) does not stop rendering. The audio service replaces each output stream with a fake AUDIO_FAKE stream that 'will continue pumping the audio data, but does not play it out anywhere'. So the page's WebRtcAudioRenderer still pulls, and WebAudio taps and MediaRecorder still receive full-level audio. The AudioContext clock still advances in real time. Per the chrome.tabs docs, tab.audible means the tab produced sound 'but it might not be heard if also muted'. In headless the audible flag was always false, so that part is unverified.

## Q: 6. Does a MediaStreamAudioDestinationNode mix keep producing frames when a source track is muted or ended, and what happens to the timeline  
[ confirmed ] Yes. The destination track is clocked by the AudioContext, so the recording timeline equals wall clock: missing input becomes silence, never a gap. Sources can be connected and disconnected freely while the MediaRecorder runs, because the recorded track never changes. When the remote sender stopped sending RTP for 3 s (replaceTrack(null)), the receiver track did NOT fire 'mute' within those 3 s and the mix contained digital silence for that span. MediaRecorder directly on a primed remote track also stayed continuous (NetEq fills silence while something pulls). Quirk: after pc2 transceiver.stop(), track.onended fired but audio from that source kept flowing into WebAudio for the remaining 4 s, until renegotiation. Do not rely on 'ended' to mean silence: disconnect the source node yourself on 'ended' or on transceiver removal. Gaps can appear only if the AudioContext itself stops: suspend(), autoplay suspension, or 'interrupted'/onerror on a physical sink failure (not tested). A context with sinkId {type:'none'} has no physical device to lose. It works the same way: running after a gesture, 45 s decoded 44.99 s. It is still autoplay-gated: suspended without a gesture.

## Q: 7. Are pc.getReceivers() tracks remote-only, with local mic tracks only in getSenders()/getUserMedia? Does any platform loop local audio bac 
[ confirmed ] By spec, yes. Creating an RTCRtpReceiver creates a new MediaStreamTrack whose 'source is a remote source provided by receiver'. The local mic track exists only as sender.track (getSenders) and as the getUserMedia track. SFUs (Meet, Teams) do not forward a participant's own audio back. Caveats where 'remote' can still be the local user: (a) Page-internal loopback PCs. The classic hack fed WebAudio output into a local RTCPeerConnection pair to get AEC (Chromium issue 40504498, now marked fixed, so it should be rarer). Both ends live in the same page, so the receiver carries locally generated audio. Detect it: the a=fingerprint in one PC's remoteDescription equals another PC's localDescription, or the PC has only host candidates. Exclude such pairs. (b) Echo or test-call bots, which are genuinely remote audio of your own voice. (c) Transceivers that are sendonly or not yet negotiated still have a receiver.track that stays muted and silent: filter on currentDirection containing 'recv' and readyState 'live'. Not verified against live Meet/Teams/Zoom pages in this task.

## Q: 8. Opus bitrate for speech transcription (32k vs 64k mono), and does whisper-cli read webm/opus directly or need ffmpeg conversion to 16 kHz 
[ confirmed ] Use mono at 24 to 32 kbps. Xiph's recommended settings put fullband at 16 kbps mono and VoIP at 10 to 24 kbps ('24 Kb/s should give fullband'). Whisper resamples to 16 kHz mono, so only content below 8 kHz matters. The incoming WebRTC audio is itself Opus at a similar rate, so 64 kbps only doubles the size: about 14 MB/h at 32k versus 29 MB/h at 64k. Chrome's default for an unspecified bitrate on a stereo destination was ~128-133 kbps stereo, so set audioBitsPerSecond and channelCount 1 explicitly. The local whisper-cli 1.9.2 (Homebrew) does NOT read WebM, and does not read Ogg/Opus even after a lossless remux. Its help says 'supported audio formats: flac, mp3, ogg, wav'; ogg means Vorbis through miniaudio. Convert with ffmpeg to 16 kHz mono PCM WAV. Piping to stdin (-) also works.
